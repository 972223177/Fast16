# 🍙 8:16 饮食法 App — 设计方案

> 版本：v0.5（MVI + feature-first + 记录合并页定稿）｜ 平台：仅 Android ｜ UI：Jetpack Compose + 像素风
> 状态：待评审。本文是**设计方案**，不含可运行实现，仅用少量代码片段说明设计意图。

---

## 0. 一句话定位

一款 **8:16 间歇性断食（8 小时进食 / 16 小时断食）** 的用餐排程与提醒 App：
用户记录**早餐时间**作为进食窗口起点 → 系统**自动推理剩余两餐（午/晚）的候选时间** → 用户**选取并微调**（含每餐「餐前准备」时长）→ 生成**当日就餐计划** → 按计划在「餐前准备」与「开始吃」两个时刻**提醒**用户。

V1 提醒是**通知 + 轻短震动**；预留**可配置震动 / 铃声 / 闹钟级**的升级扩展点。

App 常驻一个**健身像素小人**（角色），随就餐状态切换不同像素动作与交互，并在提醒时用**像素气泡**人格化地告诉你「该做什么」。

另含：**记录页（日历打卡 + 统计概览，合并页）**（本地 Room 存储）、**像素风桌面小组件**（打卡动作 + 待做任务），以及**首次启动的 8:16 引导弹窗**。

## 1. 术语与领域模型

| 术语 | 定义 |
|------|------|
| **进食窗口** | 8:16 中的「8」，从早餐时间起算，持续 `windowHours`（默认 8h），窗口内可进食，窗口外断食 |
| **早餐时间（锚点）** | 进食窗口的起点，用户记录，是全流程唯一输入 |
| **就餐计划（MealPlan）** | 某一天的一整天安排：窗口起止 + 三餐明细 |
| **餐次（Meal）** | 一餐（早 / 午 / 晚），含「开始吃时刻」「餐前准备时长」两个核心字段 |
| **餐前准备（PREP）** | 用餐前的备餐阶段（自己做主食 + 菜），时长为 `prepMinutes`，在计划生成时由用户调节 |
| **开始吃（EATING）** | 用餐开始时刻，即「餐次时间」 |
| **提醒（Reminder）** | 在 PREP / EATING 两个时刻分别触发的通知；V1 = 通知 + 固定轻短震动（单次 ~80ms） |
| **提醒模式（ReminderMode）** | 每餐提醒的呈现方式：`NONE / NOTIFY / VIBRATE / SOUND / ALARM`（V1 实现 NOTIFY + 固定轻震；可配置 VIBRATE / SOUND / ALARM 为扩展点） |
| **健身像素小人（角色）** | 首页常驻的像素角色，状态由「当前时间 × 今日计划」实时派生，随就餐阶段切换动作 |
| **像素气泡（SpeechBubble）** | 角色旁的短文案气泡，提醒/交互时出现，人格化说明「该做什么」 |
| **打卡记录（CheckIn）** | 用户对某日某餐「已完成进食」的确认记录，含时间戳；日历与连续统计的数据源 |
| **连续打卡（Streak）** | 连续「当日三餐全完成」的天数，由打卡记录派生 |
| **桌面小组件（Widget）** | 主屏卡片，展示今日三餐打卡状态 + 待做任务，支持一键打卡（Glance 实现） |
| **首次启动引导（Onboarding）** | 首启弹窗，像素风说明「什么是 8:16 饮食法」，看完置 `onboarding_seen` |

### 餐次状态机

```
            prep 时刻到             eat 时刻到            用户标记/自动归档
 SCHEDULED ──────────────► PREPARING ──────────────► EATING ──────────────► COMPLETED
   (已排程)                 (备餐中)                   (进食中)                (已完成)
```

- 每个 `Meal` 有两个**触发时刻**：`prepTime = mealTime − prepMinutes` 与 `mealTime`。
- `prepMinutes == 0` 时无 PREP 阶段，直接 `SCHEDULED → EATING`。
- 状态仅用于**当日前台 UI 展示**（进度、高亮）；后台提醒不依赖状态，只依赖已排程的闹钟。
- **角色状态（§8.6）与该状态机同源派生，不单独持久化。**
- **打卡（CheckIn）是该状态机「COMPLETED」的触发源之一**：打卡成功 → 对应 `Meal` 置为 `COMPLETED`。

## 2. 需求清单

### 2.1 功能需求（FR）

| 编号 | 需求 | 说明 / 验收要点 |
|------|------|----------------|
| FR-1 | 记录早餐时间 | 用户进入「新建计划」，输入早餐时间（默认 = 当前时间，可选具体时刻）；此时间即进食窗口起点；可**一键自动打卡早餐**（记录即已吃，默认开，可关） |
| FR-2 | 自动推理剩余两餐 | 依据早餐时间 + 规则（见 §7），生成**多套候选方案**（如「均衡 / 午餐偏早 / 晚餐偏晚」） |
| FR-3 | 候选方案选取 | 用户从候选方案中选择一套（一键选中，无需逐个填时间） |
| FR-4 | 逐餐微调 | 选中后可分别调整午/晚的**用餐时间**与**餐前准备时长**（午/晚默认备餐 30min / 45min，可改 0~120min） |
| FR-5 | 生成就餐计划 | 确认后生成 `MealPlan`，持久化本地，并**立即排程全部提醒** |
| FR-6 | 提醒（V1） | 到 PREP 时刻发「餐前准备」通知；到 EATING 时刻发「开始吃」通知；通知同步带**轻短震动**（单次 ~80ms）；铃声与可配置震动模式为 M3 扩展 |
| FR-7 | 今日计划首页 | 展示今日窗口、三餐时间轴、当前状态（备餐中/进食中）、断食剩余时间 |
| FR-8 | 计划管理 | 查看历史/当日计划；编辑（改时间后重排提醒）；删除（撤销该计划全部提醒） |
| FR-9 | 设置 | 窗口时长（默认 8h）、餐间隔下限、晚餐距窗口结束缓冲、每餐默认备餐时长、提醒模式默认值 |
| FR-10 | 权限引导 | 首次使用时申请通知权限（Android 13+ `POST_NOTIFICATIONS`）与精确闹钟权限（`SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`） |
| FR-11 | 健身像素小人 | 首页常驻角色，随就餐状态（待机/断食/备餐/进食/休息）切换不同像素动作与差异化交互 |
| FR-12 | 像素气泡人格化说明 | 提醒/交互时以像素气泡给出 ≤20 字的「该做什么」提示；**通知文案与气泡同源**，保证一致 |
| FR-13 | 日历化打卡记录 | 月历视图展示每日三餐打卡状态（●已打卡 / ○未打卡 / - 无计划）；打卡记录**本地 Room 存储** |
| FR-14 | 坚持打卡统计视图 | 展示连续打卡天数、完成率等；**已定：与日历合并为「记录」页**（统计概览在上，月历在下，底部 3 Tab） |
| FR-15 | 桌面小组件（Widget） | 主屏像素卡片：今日三餐打卡状态 + 待做任务（下一餐/备餐/断食剩余），支持一键打卡 |
| FR-16 | 首次启动引导弹窗 | 首次启动弹**像素风弹窗**说明「什么是 8:16 饮食法」；关闭后置 `onboarding_seen` 不再自动弹，可于设置中重看 |

### 2.2 非功能需求（NFR）

| 编号 | 需求 | 说明 |
|------|------|------|
| NFR-1 | **精确到分钟** | 提醒必须准点（±1min 内），需适配 Doze/App Standby：用 `setExactAndAllowWhileIdle` |
| NFR-2 | **离线可用 / 纯本地** | 无账号、无后端；全部数据在本地（Room + DataStore），不联网 |
| NFR-3 | **隐私** | 饮食数据不出设备，无埋点上传（除非用户后续要求） |
| NFR-4 | **可扩展** | 提醒方式（铃声/震动/闹钟）与计划类型（自定义窗口、多餐）可插拔演进，不推翻现有数据模型 |
| NFR-5 | **重启/时区健壮性** | 设备重启、改时区/改时间后提醒不丢（BOOT/时区广播重排） |
| NFR-6 | 性能 | 冷启动 < 1s；UI 全程 60fps（像素动画用步进帧，避免过度插值） |

### 2.3 明确不做（V1 范围外）

- ❌ 断食历史统计图表（统计**视图**在范围，深度图表/洞察不在）
- ❌ 云同步 / 多设备 / 账号体系
- ❌ 铃声音乐库、完整闹钟页（仅预留接口）
- ❌ 热量 / 食谱 / 营养素建议
- ❌ 通知栏常驻进度（列为后续候选）

## 3. 核心流程

> 完整流程图（Mermaid）见 [[8-16饮食法App-流程图]]。

```
用户打开 App
   │
   ▼
[首次启动?] 是 → 像素风弹窗「什么是 8:16 饮食法」
   │
   ▼
[新建计划] 输入早餐时间（默认=现在）
   │
   ▼
系统推理 → 生成候选方案（均衡/午餐偏早/晚餐偏晚）
   │
   ▼
用户选取一套 → 逐餐微调（午/晚时间 + 备餐时长）
   │
   ▼
[生成计划] → 持久化(MealPlan + Meals) → 排程全部提醒(AlarmManager)
   │
   ▼
[今日首页] 展示时间轴 + 断食计时 + 当前状态 + 健身像素小人
   │
   ▼  (prep 时刻) ──► 通知(含轻短震动)「餐前准备：开始做主食和菜」＋ 角色切「备餐」动作 + 气泡
   ▼  (eat  时刻) ──► 通知(含轻短震动)「开始吃 🍚」＋ 角色切「进食」动作 + 气泡
   │
   ▼  吃完后：用户打卡（通知动作 / App 内 / 桌面小组件）
   │
   ▼
[打卡记录] 写 Room(check_ins) → 对应 Meal 置 COMPLETED → 记录页/Widget 自动刷新
```

**关键交互决策**：V1 以「当天早餐时记录」为主流程，因此**早餐的餐前准备默认为 0**（此刻已在吃）。若未来支持「前一晚预排次日计划」，早餐备餐才具备意义——数据模型已兼容（见 §6），无需返工。

## 5. 架构设计

### 5.1 分层（Feature-First + MVI，单模块）

采用 **feature-first**：每个功能以 `feature/<name>/` **自治**（各自持有 UI + 专属领域/数据）；跨功能共享才进 `core/` 与共享 `domain/`、`data/`。小体量 App 保持**单 Gradle 模块**（目录级自治，日后可平滑拆 Gradle 模块）。

```
com.ly.fast16/
├── core/                        # 全 App 共享，不含业务
│   ├── designsystem/            # PixelTokens + Pixel* 组件家族 + PixelBubble
│   ├── character/               # 小健：CharacterState + SpeechCatalog + 精灵渲染
│   ├── scheduling/              # AlarmManager 封装 + PlanScheduler + ReminderChannel
│   ├── notification/            # 通知 + 轻短震动
│   ├── time/                    # 时间工具（Instant/LocalTime 换算、整分钟对齐）
│   ├── navigation/              # 类型安全路由表
│   └── di/                      # Koin Module（core 装配）
├── domain/                      # 跨 feature 共享业务（纯 Kotlin，无 Android 依赖）
│   ├── model/                   # MealPlan / Meal / CheckIn / 枚举（状态机）
│   ├── schedule/                # 时间推理算法（候选生成、约束校验）★ 可单测
│   ├── stats/                   # 连续打卡/完成率计算（gap 检测）★ 可单测
│   └── usecase/                 # GeneratePlan / ReschedulePlan / CheckIn / ...
├── data/                        # 跨 feature 共享的数据实现
│   ├── local/                   # Room Entity / DAO（Plan / Meal / CheckIn）/ DataStore
│   └── repository/              # PlanRepository / CheckInRepository（实现）
└── feature/                     # feature-first：每 feature 自治（内部结构见下）
    ├── onboarding/              # 首次引导弹窗（8:16 说明）
    ├── home/                    # 今日首页（时间轴 + 断食计时 + 小健）
    ├── create/                  # 新建计划（早餐→候选→微调→生成）
    ├── record/                  # 记录页（统计概览 + 日历，合并页）
    ├── settings/                # 设置
    └── widget/                  # Glance 桌面小组件
```

**feature 内部结构（MVI 四件套 + 可选层）**：

```
feature/home/
├── ui/
│   ├── HomeIntent.kt            // sealed：用户/系统意图（如 CheckIn(meal) / NewPlan）
│   ├── HomeState.kt             // sealed UiState：Loading / Content(...) / Error
│   ├── HomeReducer.kt           // 纯函数 (State, Intent) → State，可单测
│   ├── HomeViewModel.kt         // 收 Intent → 调 UseCase/副作用 → reduce → StateFlow
│   └── HomeScreen.kt            // 只渲染 State，只发 Intent
├── domain/                      // 该 feature 专属用例（可选，小功能可并入 ui）
└── data/                        // 该 feature 私有数据源（可选，默认走共享 data/）
```

**依赖纪律（review 红线）**：
- `feature → domain ← data`；feature 之间**禁止横向依赖**（record 需要打卡 → 必须走共享 `domain` 的 `CheckInUseCase`，不许 import 别的 feature）。
- `core` 只放共享基建；业务组件只引用 `core/designsystem` 的 tokens，不直接引用 M3 默认值。
- **Reducer 必须是纯函数**（无 Android/IO/时间源），State 只经 Reducer 变更。

### 5.2 状态管理（MVI 单向数据流）

```
View ── onIntent(Intent) ──► ViewModel
                              │ 订阅 Intent（Channel / 方法入口）
                              ▼
                    调 UseCase 执行副作用（写库 / 排程 / 通知 / 震动）
                              │
                              ▼
              Reducer 纯函数 (State, Intent) → State
                              │
                              ▼
            StateFlow<UiState> ──► Compose 渲染（UI = State 的投影）
```

- **Intent（sealed）**：意图的唯一入口，如 `HomeIntent.CheckIn(mealType)`、`HomeIntent.RecordBreakfast(time)`、`HomeIntent.DemoCharacter(state)`；系统事件（闹钟触发、打卡完成）同样转为 Intent。
- **State（sealed UiState）**：`Loading / Content / Error`，不可变；`Content` 内含渲染所需全部数据（今日计划、角色状态、断食剩余等）。
- **Reducer（纯函数）**：`(State, Intent) → State`，无 IO、无 Android 依赖、无时间源（时间由调用方注入），放 `domain` 或 feature 内，单测覆盖全部 Intent。
- **副作用（Side Effect）**：写库、AlarmManager 排程、通知 + 轻短震动由 ViewModel 在收到 Intent 时调 UseCase 执行；**不放进 reducer**。
- **一次性事件**（跳转、Toast、震动反馈）走独立 `Channel`，不塞进持久 State。
- **角色状态 / 日历 / 统计**同样走这条链：由 `todayPlan / check_ins / now` 派生后进入 `Content`，UI 只渲染。

### 5.3 调度层设计（核心扩展点）

```
                   ┌────────────────────────────────────────┐
 MealPlan ────────►│ PlanScheduler.schedule(plan)            │
                   │   对每个 Meal 的 PREP/EATING 时刻        │
                   │   经 AlarmManager 注册精确闹钟           │
                   └───────────────┬────────────────────────┘
                                   ▼
                        AlarmReceiver（BroadcastReceiver）
                                   │ 读取 alarm 携带的 mealId + phase
                                   ▼
                   ReminderChannel.trigger(meal, phase)   ← 策略接口
                                   │
              ┌────────┬───────────┼───────────┬─────────────┐
              ▼        ▼           ▼           ▼             ▼
```

### 6.4 打卡记录（Room 表）

```kotlin

    indices = [Index(value = ["date", "meal_type"], unique = true)]

    @PrimaryKey(autoGenerate = true) val id: Long = 0,

    val checkedAtEpoch: Long,    // 打卡时间戳
```

### 6.5 连续打卡统计（派生，无独立表）

- **完成日**定义：当日三餐均存在 `CheckIn` 记录。
- **连续打卡天数（Streak）**：从今天（若今天尚未完成则从昨天）向前连续「完成日」的天数。
- **统计口径（V1）**：连续天数、本月完成率（完成日数 / 天数）、本周完成率。
- **计算方式**：完成率用 SQL 聚合（`COUNT` + 日期窗口）；**连续天数**用「拉取近 N 天完成日集合 → 内存回溯做 gap 检测」，逻辑放在 `domain/stats/`，纯函数可单测，**不落地**避免双写漂移。

## 7. 时间推理算法（候选生成）

### 7.1 输入与约束

- 输入：早餐时间 `B`（即 `windowStart`）
- 常量/偏好：`W`（窗口时长，默认 8h）、`minGap`（默认 3h）、`bufferEnd`（晚餐距窗口结束缓冲，默认 30min）
- 窗口：`[B, B + W]`
- 约束：
  1. `lunch ≥ B + minGap`（早餐后至少隔 minGap）
  2. `dinner ≥ lunch + minGap`
  3. `dinner ≤ B + W − bufferEnd`（晚餐不能贴死窗口末端）

### 7.2 候选方案（3 套预设）

设窗口长度 `L = W − bufferEnd − minGap`（可用于午/晚排布的总弹性）：

| 方案 | 午餐 `lunch` | 晚餐 `dinner` | 语义 |
|------|-------------|---------------|------|
| **均衡**（默认） | `B + W/2` | `lunch + minGap` 再向窗口尾靠 → `min(B+W−bufferEnd, lunch+minGap+0.5·L)` | 均匀分布 |
| **午餐偏早** | `B + minGap + 0.25·L` | `lunch + minGap` | 上午早吃，午间长 |
| **晚餐偏晚** | `B + minGap + 0.75·L` | `B + W − bufferEnd` | 把晚餐推到窗口允许的最晚 |

> 具体数值（默认参数，B=8:00，W=8h，minGap=3h，bufferEnd=30min → 窗口 8:00–16:00，L=W−bufferEnd−minGap=4.5h）：
> - 均衡：午 12:00（B+W/2），晚 15:30（min(硬尾 15:30, lunch+minGap+0.5·L=17:15)）
> - 午餐偏早：午 12:07（earliest 11:00 + 0.25·L，向下取整分钟），晚 15:07（lunch+minGap）
> - 晚餐偏晚：午 12:30（lunchUpper=硬尾−minGap=12:30 回拉），晚 15:30（硬尾）

**✅ 已确认（决策 #1）**：采用语义 (A) —— **早餐时间严格 = 进食窗口起点**。因此晚餐会落在下午（默认参数下约 15:00–15:30），这是产品既定行为：首页与文案需**正向传达**（如「早吃早断食」），不引导用户把晚餐后移出窗口。若日后想放宽，`W / minGap / bufferEnd` 已参数化，仅需扩展语义，不改表结构。

### 7.3 微调校验（FR-4）

用户改任何时间/时长时，实时校验上述 3 条约束；违反时给出像素风提示（如红框闪烁 + 文案「午餐需在 11:00 之后」），并阻止生成。

## 8. 像素风 UI 设计系统

### 8.1 设计原则

1. **整数像素网格**：所有尺寸取 8 的倍数（8/16/24/32…），禁用亚像素与抗锯齿。
2. **有限调色板**：全 App 只用一版固定像素色板，不引入连续渐变（渐变用**阶跃色带**模拟）。
3. **步进动效**：动画走「离散帧 / 阶跃」，不做平滑缓动；交互反馈用闪烁、抖动、帧切换。

### 8.2 调色板（参考 PICO-8 / NES 感）

| 角色 | 色值 | 用途 |
|------|------|------|
| 背景深 | `#0f0f1a` | 全局背景（暗色优先，护眼 + 像素感强） |
| 面板 | `#1a1c2c` | 卡片/面板底 |
| 主绿 | `#38b764` | 「开始吃」、进行中、成功、**已打卡** |
| 主黄 | `#ffcd75` | 「餐前准备」、待处理、**待打卡** |
| 主红 | `#b13e53` | 断食中、警示、错误 |
| 主蓝 | `#41a6f6` | 信息、链接、选中 |
| 白 | `#f4f4f4` | 正文、图标高亮 |
| 灰 | `#7b7b8c` | 次要文字、禁用、**无计划** |

> 落地方式：在 M3 主题上覆写 `ColorScheme`，并另建 `PixelTokens`（`PixelColors/PixelShape/PixelType/PixelMotion`），业务组件**只引用 tokens，不引用 M3 默认值**。

### 8.3 字体

- **数字/英文/计时器**：像素字体 `Press Start 2P` 或 `Silkscreen`（开源可商用）。
- **中文**：纯中文像素字体免费可商用者少。建议：
  - 标题/强调用 `ZCOOL 系列`（站酷，可商用）或 `Smiley Sans 得意黑` 做「近像素」观感；
  - 正文用系统默认黑体以保证可读性；
  - **落地前确认字体授权**（此点为评审项）。

### 8.4 图标与精灵

- 图标一律 16×16 或 32×32 像素 PNG 位图，或 Canvas 直接画像素格。
- Compose 侧渲染关键：`Image(..., filterQuality: FilterQuality.none)`，缩放取**整数倍**，避免模糊。

### 8.5 动效规范（像素步进）

| 动效 | 实现要点 |
|------|----------|
| **断食进度条** | 分块像素条：N 格，进度 = `floor(progress·N)`，一格一格点亮，不做平滑填充 |
| **计时器数字** | 秒级整秒刷新天然是「步进感」；字体用 `Press Start 2P`，数字变化即跳动 |
| **闪烁提示** | alpha 在 `1.0 ↔ 0.0` 之间**阶跃**（用整数帧控制，非线性插值），模拟像素闪烁 |
| **精灵帧动画** | 图标 2~4 帧循环（如饭团眨眼、铃铛摇晃、小人动作），用 `Animatable<Int>` 步进帧索引 |
| **页面切换** | 像素淡入 / 扫描线 wipe / 黑屏闪白一帧（可选），避免 Material 默认的平滑过渡 |
| **交互反馈** | 按钮按下位移 1 像素 + 阴影剥离（纯 CSS 感的「按下沉」）；选中态用主黄描边 |
| **打卡反馈** | 打卡成功瞬间：该餐图标「跳一格」+ 气泡「干得漂亮！」+ 轻短震动（V1，单次 ~80ms） |

### 8.6 健身像素小人 + 像素气泡（角色系统）

#### 角色设定（人格化）

- 名称：暂定「**小健**」（可换）；人格：**元气鼓励型教练**——短句、口语、正向，不焦虑、不爹味，常用像素 emoji（🍚🍳💪）。
- 位置：今日首页主角；提醒时以「角色头像 + 气泡」同时出现在页面与通知中。

#### 角色状态 ↔ 就餐状态映射（实时派生，不落库）

| 角色状态 | 触发条件 | 像素动作（帧动画） | 气泡示例 |
|---------|---------|------------------|----------|
| 待机 `IDLE` | 今日无计划 / 未到首餐 | 原地呼吸 + 眨眼 | 「来记录早餐，开启今天第一餐吧！」 |
| 断食 `FASTING` | 窗口外 / 两餐之间 | 小跑 / 举铁 / 冥想（随机） | 「断食中，再坚持 {剩余} 就开饭啦！」 |
| 备餐 `PREP` | 到达 prepTime | 切菜 / 颠锅 | 「准备时间！主食和菜做起来 🍳」 |
| 进食 `EATING` | 到达 mealTime | 吃饭 / 咀嚼 | 「开饭啦！慢慢吃，别着急～」 |
| 休息 `REST` | 当天全部完成 | 拉伸 / 比赞 | 「今天完成啦，干得漂亮！💪」 |

> 派生优先级（与 `domain` 纯函数一致）：无计划 → `IDLE`；进行中 → `PREP` > `EATING`；三餐全完成 → `REST`；其余（两餐之间/窗口外）→ `FASTING`。

#### 差异化交互效果

1. **点击角色**：触发彩蛋动作（跳跃/举铁）+ 随机一句鼓励语气泡。
2. **状态切换**：角色帧切换 + 气泡「弹出」（scale 0→1 阶跃，非平滑）。
3. **提醒到达**：角色「跳到气泡旁」+ 气泡弹出；通知同步携带**角色头像与同一句文案**。

#### 像素气泡（PixelBubble）

- 外观：像素阶梯圆角 + 三角尾巴，白底 + 2px 黑描边，文字用像素字体。
- 文案规则：**≤ 20 字**、一句话说明「该做什么」、带角色人格。
- 文案目录 `SpeechCatalog`：按 `(phase, mealType)` 键控，模板支持变量 `{餐名} {剩余时间} {备餐分钟}`，同键多条随机轮换；**通知文案与气泡同源**（保证一致）。

#### 工程要点

- 状态派生：`CharacterState = f(now, todayPlan)`，与餐次状态机同源，**无独立持久化**。
- 精灵资源：**Q 版人形 16×20，蓝色运动服 `#41a6f6` + 黄纽扣**（角色基线见 [[8-16饮食法App-基建与UI骨架]] §2.3）；`CharacterSpriteSheet` 5 状态 × 2~4 帧，`FilterQuality.none` + 整数倍缩放；肤色/发色为角色专属色（非 UI 令牌）。
- 待机动效（UI 原型 v0.1 定稿）：**自然眨眼（约 3.1s 闭 1 帧）+ 呼吸起伏（约 1.3s 沉 1px）**，不做高频硬闪。

### 8.7 桌面小组件（Glance · 像素风）

#### 内容结构（卡片式）

- **打卡状态行**：每餐一个像素图标（● 已打卡=绿 / ○ 待打卡=黄 / - 无计划=灰），**点击该餐即打卡**。

- **主操作**：`打卡`（对当前可打卡的餐）+ `打开 App` 入口（跳转对应页面）。

#### 技术要点与约束（Glance 的「能 / 不能」）

| 能力 | 说明 |
|------|------|
| 写法 | `GlanceAppWidget` + `GlanceAppWidgetReceiver`，用 `@Composable` 声明式写 UI（与 App **共用 `PixelTokens` 色值/字号常量**） |
| 更新 | 手动 `update` + 定时 `updatePeriodMillis`（**系统最小约 30min**，无法秒级刷新倒计时，接受「分钟级」粒度） |
| 交互 | 仅 `clickable` → `actionStartActivity` / `actionRunCallback`；**无动画、无自定义 Canvas、无 FilterQuality** |
| 像素风 | 用**像素位图图标**（`ImageProvider` → Bitmap）+ 纯色块/阶梯圆角拼像素感；文字用系统字体（Widget 难用自定义字体，可接受或预渲染文本位图） |
| 打卡动作 | `actionRunCallback` → `BroadcastReceiver` → `CheckInUseCase.checkIn()` → 更新 Widget（SSOT 写库后由 Flow 驱动刷新） |

> ⚠️ Glance **不能做平滑动画与逐秒刷新**；像素风的「步进感」在 Widget 里靠**静态像素位图 + 纯色块**体现，而非动画——这与 App 内动效能力不同，UI/UX 草稿阶段需对齐该预期。

### 8.8 首次启动引导弹窗（8:16 说明）

#### 触发与持久化

- 触发条件：`onboarding_seen == false`（DataStore），即首次启动（或清除数据后）。
- 关闭行为：点「知道了，开始使用」→ 置 `onboarding_seen = true`，**不再自动弹出**；可在设置页「查看 8:16 说明」重看。

#### 弹窗内容（像素风）

```
┌─────────────────────────────┐
│  🍙 什么是 8:16 饮食法？      │
│                             │
│  一天 24 小时                 │
│  ┌────────┬───────────────┐  │
│  │ 进食 8h│  断食 16h      │  │   ← 像素分块条示意
│  └────────┴───────────────┘  │
│                             │
│  在 8 小时窗口里吃完三餐：      │
│  记录早餐 → 自动排午/晚        │
│  到点提醒「备餐 / 开吃」        │
│  吃完打卡，坚持就有记录         │
│                             │
│  [ 知道了，开始使用 ]          │
└─────────────────────────────┘
```

- 角色「小健」举牌出场 + 气泡一句引导（如「跟我一起，早吃早断食！」）。
- 文案要点：**只做客观解释，不做医疗功效承诺**——「8:16 是一种进食时间安排：8 小时进食、16 小时断食」，避免「减肥/治愈」等健康声明。

#### 实现要点

- Compose `Dialog` / 全屏 `Popup`，复用 `PixelTokens`；标题用像素字体，正文用系统字体保证可读性。
- 弹窗出现动效：黑屏闪白一帧 → 弹窗「弹出」（scale 0→1 阶跃），关闭时像素淡出。
- 若用户跳过（返回键/点外部），同样置 `onboarding_seen = true`，不强拦。

## 10. 风险与待确认项

1. **精确闹钟权限**：`SCHEDULE_EXACT_ALARM` 在部分厂商 ROM 需用户手动放行、可能被节电策略杀掉。需在 M1 早期真机验证（尤其小米/华为/vivo）。
2. **「早餐=窗口起点」导致的早晚餐**：已确认语义 (A)，晚餐落在下午属既定行为；需在文案/设计上正向传达，避免用户困惑。
3. **中文像素字体授权**：`Press Start 2P` 是英文像素；中文需要选可商用方案并确认授权。
4. **Navigation 2 类型安全 vs Navigation 3**：V1 用成熟稳定的 Navigation 2 类型安全路由即可，若你要尝鲜可上 Navigation 3（评估其稳定性后再定）。
5. **精确闹钟 vs WorkManager 兜底**：WorkManager 无法保证分钟级，只能做「每日重算 + 兜底」，需确认是否需要「当日计划跨日重算」场景。
6. **像素精灵美术资源**：小人的 5 状态 × 每状态 2~4 帧，需产出统一风格位图；建议先占位（单色方块）再替换正式素材，避免阻塞主线。
7. **Room 3.0 最低系统版本**：minSdk 由 API 21 提到 23，需确认目标机型覆盖；个人工具建议 minSdk 24+。
8. **Glance 小组件能力边界**：无动画、无逐秒刷新（定时最小约 30min）、难用自定义字体，像素风需用「静态位图 + 纯色块」实现，与 App 内动效预期不同。
9. **8:16 说明的合规性**：引导文案仅做客观解释，避免健康功效宣称；如需更严谨表述，建议配一句「个体差异，请结合自身情况」。

## 11. 已确认决策（v0.5）

| # | 决策 | 结论 |
|---|------|------|
| 1 | 窗口语义 | 早餐时间**严格 = 进食窗口起点**（语义 A） |
| 2 | 提醒粒度 | V1 = **通知 + 固定轻短震动**（单次 ~80ms）；铃声与**可配置**震动模式预留 `ReminderChannel` 扩展入口，归 M3 |
| 3 | 依赖注入 | **Koin**（纯 Kotlin DSL，轻量） |
| 4 | 角色 | 新增**健身像素小人**：随就餐状态切换交互；提醒时用**像素气泡**人格化说明该做什么 |
| 5 | 打卡存储 | 打卡记录用 **Room 3.0（最新稳定）** 本地存储；DataStore 仅存偏好/Widget 配置 |
